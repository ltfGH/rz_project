# 配置驱动的离线业务软件生成器设计

## 1. 背景

现有生成器以固定四页面 HTML 模板为基础，由模型直接修改页面、脚本和材料内容，数据保存在浏览器 `localStorage`。这种方式适合演示型应用，但难以稳定生成可长期使用的离线业务软件，主要问题包括：

- 数据模型、页面和材料容易不一致；
- 模型可以直接改写大量实现代码，结果难以约束和复用；
- 固定页面和通用数据库图无法表达真实的多模块业务系统；
- 状态流转、跨表事务、权限和审计缺少统一实现；
- 不同主题的生成质量取决于模型临场发挥，难以形成稳定验收标准。

目标参考项目为“企业服务智能运维平台系统”。它采用 Electron + SQLite，包含多角色、资产、告警、工单、巡检、知识、交接、审计和备份等模块。新生成器首个可交付版本生成的软件，需要达到与该参考项目相近的功能规模和交付完整度。

## 2. 目标

生成器面向以软著申报交付为主要场景、同时要求可以长期实际使用的 Windows 离线业务软件。

首版目标：

- 接受任意软件主题输入，并将其映射到经过验证的业务原型及原型组合；
- 在生成代码前形成可审阅、可修改、可校验的业务蓝图；
- 生成独立的 Electron + SQLite 桌面程序，运行时不依赖生成器、模型或网络；
- 单个生成项目通常包含 8 至 15 个功能模块、8 至 20 张业务及系统表，以及 2 至 4 条完整业务流程；
- 支持真实的持久化、关系约束、状态流转、跨表事务、审计、备份和恢复；
- 从同一份蓝图和实际运行结果生成源码、安装包、截图、手册、功能表和数据库设计材料；
- 生成结果必须通过自动测试和安装生命周期验证后才能发布。

规模数字是目标区间，不是机械限制。业务需要时可以超出区间，但不得通过空菜单、重复页面或无实际作用的表来凑数量。

## 3. 非目标

首版不包含：

- 面向最终用户的任意拖拽式低代码设计器；
- 依赖服务器、云数据库或外部低代码平台的运行方式；
- 让模型临时生成未经审核的领域插件并直接交付；
- 对医疗诊断、危险品控制等专业规则作未经人工确认的正确性承诺；
- 自动接入生产设备、第三方业务系统或外部大模型服务。

## 4. 总体方案

采用“配置驱动底座 + 经过测试的业务插件”的混合架构。

低代码配置负责通用能力，包括菜单、实体、字段、关系、列表、表单、筛选、基础统计、角色权限和简单状态转换。领域插件负责不能由普通 CRUD 安全表达的能力，包括批次库存、巡检整改、工单闭环、审批归档和跨实体事务。

模型只负责：

- 理解用户主题并选择业务原型；
- 生成结构化业务蓝图；
- 根据校验错误修订蓝图一次；
- 生成与已确认蓝图一致的业务说明文字和演示数据定义。

模型不得修改数据库运行时、权限核心、备份恢复、安装链、审计机制或其他底座核心代码。

## 5. 系统边界

### 5.1 生成器

生成器负责：

1. 收集软件主题、使用对象和补充要求；
2. 匹配并组合业务原型；
3. 调用模型生成业务蓝图；
4. 校验蓝图并向用户展示可读摘要；
5. 接受用户修改或确认；
6. 根据蓝图组装桌面程序、配置和领域插件；
7. 创建 SQLite 结构及演示数据；
8. 执行单元、集成、端到端和安装测试；
9. 从实际项目生成软著材料和安装包；
10. 发布完整交付目录及验证报告。

### 5.2 生成的软件

每个生成项目是独立的离线桌面程序，包含：

- Electron 桌面外壳；
- 隔离的预加载 IPC 接口；
- SQLite 数据库及版本迁移；
- 元数据驱动的页面运行时；
- 权限、流程、审计和备份等标准服务；
- 按蓝图启用的领域插件；
- 项目专属配置、演示数据和测试；
- 独立安装、卸载和用户数据目录。

生成的软件不读取生成器目录，也不需要 Codex、Node 开发环境或网络连接。

## 6. 首版业务原型

首版内置六类业务原型：

1. **台账与资产**：分类、资产、责任人、状态和生命周期。
2. **巡检与整改**：计划、检查项、执行记录、异常、整改和复核闭环。
3. **工单与服务**：受理、分派、处理、复核、关闭和 SLA。
4. **库存与批次**：物料、批次、入库、领用、退库和库存预警。
5. **项目与任务**：项目、里程碑、任务、进度、风险和交付物。
6. **申请与归档**：申请、审批、证照、文件、到期提醒和归档。

一个软件可以组合多个原型。例如：

- 电梯维保 = 台账与资产 + 巡检与整改 + 工单与服务；
- 实验室耗材 = 库存与批次 + 申请与归档；
- 企业运维 = 台账与资产 + 工单与服务 + 巡检与整改；
- 工程项目 = 项目与任务 + 申请与归档。

原型固定经过验证的流程骨架和不变量，项目配置决定名称、字段、检查项、角色、期限、严重程度和允许调整的状态。行业特殊规则必须由已有领域插件提供。

## 7. 业务蓝图

业务蓝图是模型与底座之间唯一的生成契约。蓝图采用带版本号的结构化 JSON，并由 JSON Schema 和语义校验器共同验证。

蓝图至少包含：

- 软件标识、名称、版本、定位和使用边界；
- 目标用户及是否启用登录；
- 选用的业务原型、组合关系和领域插件；
- 功能模块、菜单、页面和导航顺序；
- 实体、字段、类型、默认值、唯一约束和实体关系；
- 列表列、筛选项、表单布局和详情关联信息；
- 角色、操作权限和数据范围；
- 状态机、操作条件、事务动作和禁止条件；
- 仪表盘指标、报表口径和导出定义；
- 演示数据规模及可重复生成的种子；
- 材料所需的软件用途、功能和技术说明。

蓝图校验分为两层：

- 结构校验：字段类型、必填属性、引用和枚举符合 Schema；
- 语义校验：关系目标存在、状态机可达、每条流程可完成、角色具备完成流程的权限、删除规则不破坏历史、插件参数完整。

模型可根据校验摘要自动修订蓝图一次。第二次仍失败时停止生成，并向用户展示具体问题。

## 8. 权限与审计

权限系统是底座标准能力，但由业务蓝图决定是否启用：

- 多人协作项目默认启用登录和角色权限；
- 个人工具可以关闭登录；
- 角色名称和权限由业务原型提供，蓝图只能在约束范围内调整；
- 密码只保存带随机盐的安全摘要；
- 渲染层不能直接访问数据库；
- 关键新增、修改、删除、导出和状态转换统一写入审计记录；
- 审计记录不通过普通业务页面删除或改写。

## 9. 数据与流程运行时

### 9.1 数据服务

数据服务统一提供：

- SQLite 连接、外键和事务；
- 参数化查询、分页和组合筛选；
- 唯一约束、引用约束和业务版本检查；
- 数据库版本迁移；
- CSV 导入前校验与事务提交；
- 一致性备份、恢复说明和数据目录管理。

### 9.2 流程引擎

流程引擎执行蓝图声明的状态机，但不接受任意脚本。每个操作由白名单动作组成，包括：

- 校验当前状态和操作者权限；
- 校验关联实体和必填处理记录；
- 在一个事务中修改多个实体；
- 写入状态事件和审计记录；
- 使用版本字段阻止旧详情覆盖新状态。

无法由白名单动作表达的流程只能调用经过测试的领域插件。

## 10. 桌面生成向导

生成器采用桌面向导为主、命令行为辅的交互形式。

向导步骤：

1. 填写软件主题、使用对象和补充要求；
2. 查看原型匹配结果及能力覆盖范围；
3. 审阅模块、实体、流程、角色和数据模型摘要；
4. 修改需求、重新生成蓝图或确认蓝图；
5. 查看生成、测试、材料和打包阶段进度；
6. 查看验证报告和交付目录。

命令行模式使用同一套服务和蓝图协议，用于自动测试、批量生成和故障诊断，不能维护另一套实现。

## 11. 不支持需求的处理

当输入主题包含现有原型和插件不能可靠实现的要求时：

1. 蓝图阶段明确列出已覆盖能力和未覆盖能力；
2. 用户可以删除或调整未覆盖要求；
3. 用户也可以取消本次生成；
4. 生成器不得用普通字段或假页面冒充未实现的专业能力；
5. 可复用的新需求由开发者实现成带测试的领域插件后进入原型库。

首版不允许模型临时生成插件代码并自动发布。

## 12. 生成流水线

完整数据流为：

`主题输入 -> 原型匹配 -> 蓝图生成 -> 蓝图校验 -> 用户确认 -> 项目组装 -> 数据库初始化 -> 测试 -> 截图 -> 材料 -> 安装包 -> 安装验证 -> 发布`

现有生成器的预检、截图、材料、安装和发布阶段可以保留其职责，但需要改为消费新项目结构和真实蓝图。现有“模型直接修改固定四页模板”的 Generate 阶段由蓝图阶段和项目组装阶段替代。

所有阶段写入同一运行日志和机器可读报告。失败时保留工作区，不发布不完整交付物。

## 13. 测试与发布门槛

每个生成项目必须通过：

- 蓝图结构和语义测试；
- 数据库建库、迁移、外键、唯一约束和事务回滚测试；
- 备份创建及可读性测试；
- 每条核心流程的正常完成测试；
- 非法状态跳转、权限拒绝和版本冲突测试；
- 通用列表、筛选、分页、表单和详情测试；
- 不同角色完成核心流程的端到端测试；
- 主要页面多尺寸截图和非空检查；
- 安装、启动、持久化、关闭重启和卸载测试；
- 源码、数据库设计、功能表、手册和截图的一致性检查；
- 申请人信息、凭据、网络依赖和虚构专业结论检查。

任一强制检查失败时不得进入发布目录。验证报告应记录蓝图版本、项目版本、测试结果、安装测试结果和交付文件摘要。

## 14. 软著材料生成

材料不再由模型独立编写，而从以下真实来源生成：

- 软件名称、用途和用户：已确认蓝图；
- 功能表：实际模块、页面和允许操作；
- 数据库设计：实际迁移及 SQLite 元数据；
- 操作手册：实际页面、流程步骤和运行截图；
- 原型设计：实际实体关系、状态机和界面布局；
- 源码材料：实际交付源码；
- 运行环境：实际打包版本、数据目录和依赖。

申请人身份、联系方式、证件和发布日期等未知信息继续使用明确的申请人填写标记，不由模型推断。

## 15. 分阶段建设

整体架构拆为五个可独立验收的子项目：

1. **蓝图协议与校验器**：定义 Schema、原型目录、组合规则和语义检查。
2. **桌面业务底座**：实现 Electron、SQLite、元数据页面、权限、审计、备份和流程引擎。
3. **六类原型与领域插件**：逐类实现并建立组合测试矩阵。
4. **生成向导与编排集成**：用蓝图替换现有直接代码生成，接入现有构建流水线。
5. **材料与验收链改造**：从实际项目生成材料，并以企业运维同规模试点完成验收。

每个子项目单独设计、计划、测试和提交。首版发布必须完成全部五项，阶段拆分不降低最终规模目标。

## 16. 首版验收

使用一个与“企业服务智能运维平台系统”规模相近的试点主题进行最终验收。验收关注：

- 功能入口数量及每个入口的实际作用；
- 数据表、关系、约束和业务记录规模；
- 多角色权限和审计是否有效；
- 至少 2 至 4 条核心流程能完整闭环；
- 安装后可离线长期保存和备份数据；
- 重启后数据和状态保持；
- 安装包、源码和材料可以独立交付；
- 文档、截图、数据模型和程序行为一致。

通过试点不代表所有行业规则自动正确。任意主题仍受首版原型和插件覆盖范围约束，未覆盖能力必须在蓝图确认阶段明确披露。
