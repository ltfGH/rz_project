# 离线桌面业务底座设计

## 1. 目标

本子项目建设一个可被业务蓝图驱动的离线桌面业务底座。底座必须长期稳定复用，不由模型为每个项目重新编写。它负责 Electron 桌面运行、SQLite 持久化、权限、审计、通用业务页面和状态流转，为后续六类业务原型及领域插件提供受控扩展接口。

本子项目完成后，应当可以使用一份不依赖领域插件的验收蓝图生成并运行一个包含关联实体、多角色和完整状态流程的桌面应用。

## 2. 非目标

本阶段不包含：

- 六类业务原型的完整领域插件；
- 任意拖拽式页面编辑器；
- 模型动态生成 React、SQL 或主进程代码；
- 现有生成器编排流程的整体替换；
- 新版软著材料生成；
- 外部服务器、云数据库或联网服务；
- 企业运维参考项目的全部业务模块。

这些能力分别属于后续的领域插件、生成向导与材料链子项目。

## 3. 技术栈

桌面底座采用：

- Electron：Windows 离线桌面运行和受控本机能力；
- React：元数据驱动的管理界面；
- TypeScript：约束蓝图、IPC、服务和组件接口；
- Vite：渲染层开发及生产构建；
- `node:sqlite`：主进程内的 SQLite 数据访问；
- electron-builder + NSIS：生成 Windows x64 安装包；
- Node 内置测试框架：核心与服务单元测试；
- Playwright：关键界面与 Electron 端到端测试。

所有依赖在构建阶段固定版本。生成的软件运行时不启动开发服务器，不需要 Node 开发环境或网络访问。

## 4. 分层架构

### 4.1 Electron 主进程

主进程负责：

- 应用和窗口生命周期；
- 安全的 BrowserWindow 配置；
- SQLite 连接、迁移和事务；
- 身份认证、会话和权限检查；
- 数据导入、导出、备份和文件选择；
- IPC 处理器注册；
- 运行日志和不可恢复错误页面；
- 生产资源路径与用户数据目录解析。

窗口必须启用 `contextIsolation`、禁用 `nodeIntegration`，并限制导航、新窗口和外部 URL。渲染进程不能直接持有数据库或文件系统权限。

### 4.2 预加载桥接层

预加载层只暴露一个带类型的 `window.businessApi`。接口按能力分组：

- `session`：登录、退出和读取当前会话；
- `metadata`：读取已确认的安全界面元数据；
- `entities`：分页查询、读取详情、新增和更新；
- `workflows`：读取允许操作和执行状态转换；
- `dashboard`：读取统计指标；
- `files`：选择导入文件和导出目标；
- `maintenance`：数据库信息、备份和受控恢复检查。

所有调用使用结构化 DTO。预加载层不暴露通用 `invoke(channel, payload)`、Node `require`、任意文件路径读写或任意 SQL。

### 4.3 业务核心层

业务核心层不依赖 Electron UI，负责：

- 蓝图加载和运行时兼容检查；
- 数据库模式生成与迁移；
- 实体字段、关系和业务版本校验；
- 参数化查询和组合筛选；
- 角色权限和数据操作授权；
- 状态机可执行性检查；
- 白名单条件及事务动作；
- 状态事件和审计记录；
- 领域插件注册及隔离调用。

核心服务接受显式上下文，包括当前用户、蓝图版本和事务句柄，不读取 React 状态或隐式全局用户。

### 4.4 React 渲染层

React 只消费预加载桥接提供的数据和安全元数据，负责：

- 应用框架、导航和路由；
- 登录和会话过期处理；
- 仪表盘、列表、筛选、分页和排序；
- 新增及编辑表单；
- 详情、关联记录和流程时间线；
- 当前状态下允许的流程按钮；
- 一致的加载、空数据、错误和权限拒绝状态。

渲染层不重复实现权限和业务校验。隐藏按钮仅改善体验，最终授权必须由主进程业务服务执行。

## 5. 源码组织

底座作为独立模板目录新增，不直接覆盖当前四页模板，避免在后续编排集成完成前破坏现有生成流程。

建议目录：

```text
engine/desktop-runtime/
  package.json
  electron-builder.yml
  tsconfig.json
  vite.config.ts
  src/
    shared/          蓝图运行时类型、DTO、错误码
    main/            Electron 生命周期、窗口和 IPC
    preload/         contextBridge 接口
    core/            数据、权限、流程、审计和插件接口
    renderer/        React 应用和通用业务组件
  tests/
    unit/            纯核心逻辑测试
    integration/     SQLite、迁移和 IPC 服务测试
    e2e/             Electron 用户流程测试
  fixtures/
    runtime-blueprint.json
```

现有 `engine/template` 和现有生成流程在本阶段保持可用。后续“生成向导与编排集成”子项目负责切换模板。

## 6. 蓝图运行时边界

桌面底座只接受蓝图校验器已经判定 `valid: true` 且 `canGenerate: true` 的蓝图。启动时仍执行轻量兼容检查：

- `schemaVersion` 是底座支持的版本；
- 蓝图摘要与构建时记录一致；
- 所声明领域插件均已安装且版本兼容；
- 数据库迁移版本不高于当前应用支持版本。

底座不接受蓝图中的任意代码、SQL、表达式或脚本。流程条件和动作只能使用蓝图协议定义的白名单类型。

## 7. 数据库设计

### 7.1 文件与连接

每个生成应用使用独立 SQLite 文件，位于 Electron `userData` 目录。数据库连接只在主进程创建。每个连接启用外键，并设置明确的繁忙等待和事务策略。

### 7.2 模式与迁移

蓝图不直接携带 SQL。构建阶段由模式编译器将允许的实体、字段、唯一约束、关系和索引转换成确定的版本化迁移。生成结果包含：

- 应用模式版本；
- 顺序迁移列表；
- 迁移内容摘要；
- 初始化演示数据的确定性种子。

迁移在事务中执行。迁移失败时回滚并阻止进入业务页面，不允许跳过失败版本继续运行。

### 7.3 通用系统表

启用相应能力时，底座创建以下系统表：

- 用户及角色；
- 会话安全状态；
- 业务状态事件；
- 操作审计；
- 数据库迁移记录；
- 应用元数据；
- 备份清单。

业务表由蓝图实体生成。表名、列名和索引名仅来自已验证的标识符，用户输入从不作为未校验 SQL 标识符使用。

### 7.4 事务与并发

普通新增和更新通过统一实体服务执行。更新操作必须携带 `version`，SQL 使用版本条件更新并递增版本；影响行数为零时返回版本冲突。

状态转换在一个事务中完成：

1. 读取并验证当前记录版本和状态；
2. 验证当前用户权限；
3. 执行白名单条件；
4. 更新主记录及相关记录；
5. 写入状态事件；
6. 写入审计记录；
7. 提交事务。

任一步失败都回滚，不留下部分状态。

## 8. 身份、权限与审计

启用登录时，密码使用随机盐 `scrypt` 摘要。登录失败采用内存和数据库状态结合的有限速策略，不在日志记录密码。

权限键沿用蓝图的 `<module>.<action>`。每次实体写入、流程执行、导出和维护操作都在主进程重新授权。

审计记录至少包含：

- 操作者 ID 和显示名称；
- 权限动作；
- 实体和记录 ID；
- 操作结果；
- 结构化、脱敏的变更摘要；
- 时间和应用版本。

审计表为追加写入，不注册普通更新或删除接口。

## 9. 元数据界面

界面采用固定、紧凑的后台管理布局：

- 左侧按业务分组的一级导航；
- 顶部软件名称、当前用户和全局维护入口；
- 统一列表页：关键词、组合筛选、分页、排序、导出和批量操作；
- 统一表单：字段类型、必填、枚举和关系选择由蓝图驱动；
- 统一详情页：基础信息、关联数据、状态事件和允许操作；
- 统一仪表盘：统计卡片、趋势、分类和待办列表；
- 统一确认对话框：危险操作必须显示影响对象和结果。

模型可以配置内容和少量主题标识，不能改变基础交互模式或注入 React 组件。特殊领域界面只能通过注册扩展槽提供。

## 10. 流程引擎

首版流程条件：

- `required_field`；
- `field_equals`；
- `relation_exists`。

首版事务动作：

- `set_field`；
- `create_record`；
- `update_related`；
- `append_event`；
- `write_audit`。

流程引擎只解释这些结构化动作，不执行 `eval`、动态函数、模板脚本或蓝图携带的 SQL。新增条件或动作必须通过代码、类型、测试和目录版本升级加入。

## 11. 领域插件接口

本阶段只定义并验证插件接口，不实现六类完整插件。插件可以注册：

- 附加迁移；
- 事务服务；
- IPC 能力；
- 特殊页面扩展槽；
- 蓝图配置校验；
- 自动化测试场景。

插件不能直接替换权限、审计、迁移或备份核心。插件调用必须经过主进程注册表，未注册插件导致应用构建失败。

## 12. 错误模型

所有可预期错误使用稳定结构：

```text
code        稳定机器码
message     可展示的中文说明
fieldErrors 可选字段错误列表
retryable   是否允许原操作重试
details     脱敏的诊断信息
```

至少区分：输入校验、未认证、权限拒绝、记录不存在、唯一冲突、版本冲突、非法状态转换、导入失败和备份失败。

不可恢复错误包括数据库损坏、迁移失败和蓝图运行时不兼容。此类错误阻止业务页面启动，展示恢复入口和日志编号，不展示原始 SQL、堆栈、密码摘要或敏感本机路径。

## 13. 备份与恢复

备份由主进程通过 SQLite 一致性机制创建，输出独立数据库文件和清单。清单包含应用 ID、应用版本、模式版本、创建时间、文件大小和摘要。

本阶段实现备份创建、清单校验和受控恢复。实际覆盖当前数据库前必须要求用户明确确认并关闭业务连接。恢复前将当前数据库移动为恢复保护副本，再原子替换备份文件并执行完整性和模式版本检查；任一检查失败时恢复原数据库并返回稳定错误码。

## 14. 打包与数据目录

使用 electron-builder 的 NSIS 目标生成 Windows x64 安装包：

- 默认按当前用户安装；
- 支持选择安装目录；
- 创建开始菜单入口，可选桌面快捷方式；
- 应用源码及资源打入 ASAR；
- 用户 SQLite 和备份不放在安装目录；
- 卸载默认保留用户数据；
- 安装包不依赖系统 Edge 或本地 Node。

本阶段新增桌面底座自身的构建及安装验证，不立即替换现有生成器的安装脚本。

## 15. 测试策略

### 15.1 单元测试

覆盖：

- 蓝图到数据库模式映射；
- 权限判断；
- 字段及关系校验；
- 状态机条件和动作；
- 版本冲突；
- 错误码和脱敏。

### 15.2 集成测试

使用临时 SQLite 文件覆盖：

- 建库和迁移；
- 外键及唯一约束；
- 分页和组合筛选；
- 跨表事务提交与回滚；
- 状态事件和审计同事务保存；
- 一致性备份及清单验证；
- IPC 输入校验和授权。

### 15.3 Electron 端到端测试

验收蓝图至少包含三个关联实体、三种角色和一条四阶段流程。端到端测试覆盖：

- 登录及角色导航；
- 列表、筛选、分页和详情；
- 新增及编辑；
- 不同角色协作完成流程；
- 非法操作被拒绝；
- 重启后数据保持；
- 备份文件创建；
- 从有效备份恢复并在失败时保留原数据库；
- 生产构建可启动且无开发服务器依赖。

### 15.4 回归要求

现有生成器 PowerShell 测试必须继续通过。桌面底座作为新增目录存在，直到后续编排集成明确切换。

## 16. 验收标准

本子项目完成的最低标准：

1. 桌面底座能加载一份通过校验的验收蓝图；
2. 能从蓝图创建真实 SQLite 表、关系、系统表和演示数据；
3. 三种角色可以通过通用界面共同完成一条完整状态流程；
4. 权限绕过、非法状态、唯一冲突和版本冲突均被主进程拒绝；
5. 状态变化和审计在同一事务中保存；
6. 数据在应用重启后保持；
7. 可以创建一致性备份，并安全恢复有效备份；
8. Playwright 覆盖核心流程并验证主要界面非空；
9. electron-builder 可以生成并验证 Windows x64 安装包；
10. 不影响现有生成器完整测试套件。

完成这些标准只表示通用底座可用。参考 Demo 规模的软件仍需后续领域插件和编排集成共同完成。
