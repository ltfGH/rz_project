# 业务原型与领域插件设计

## 1. 目标

本子项目在已完成的业务蓝图协议和离线桌面底座之上，实现六类可组合、可测试、可版本锁定的业务原型与领域插件。任意软件主题先映射到一个或多个原型，再由组合器生成完整业务蓝图；桌面底座继续负责通用数据、权限、审计、状态机和界面，插件只承担无法由普通元数据安全表达的领域事务。

首版必须交付全部六类原型，并通过单包、常用双包和“台账 + 工单 + 巡检”参考规模组合验收。

## 2. 非目标

本阶段不包含：

- 最终用户拖拽式低代码编辑器；
- 模型临时生成并执行领域代码；
- 外部服务器、云数据库或生产设备接入；
- 医疗、危化、财务会计等专业法规自动判定；
- 生成向导界面和现有编排流程切换；
- 新版软著材料生成。

未被领域包覆盖的专业要求必须保留为未覆盖需求，不能用普通 CRUD 页面冒充。

## 3. 总体结构

领域能力分为三层：

1. **原型目录**：声明原型名称、能力、依赖、兼容版本和可组合关系。
2. **蓝图片段**：声明实体、字段、模块、角色、流程、仪表盘及扩展点使用。
3. **运行时插件**：实现需要显式事务和领域不变量的服务，并注册受控 UI 扩展。

建议目录：

```text
engine/domain-packs/
  package.json
  src/
    composition/             依赖解析、冲突检测和蓝图合并
    registry/                原型与插件目录
    shared/                  领域包接口、错误码和测试工具
    archetypes/
      asset_registry/
        catalog.json
        blueprint.json
        runtime/
        ui/
        seed/
        tests/
      work_order_service/
      inspection_rectification/
      inventory_batch/
      project_task/
      application_archive/
  tests/
    combinations/
    reference-scale/
```

领域包作为独立开发包存在，不直接写入桌面底座。后续编排集成阶段负责将选中的蓝图片段、插件代码和 UI 扩展组装到生成项目。

## 4. 领域包清单

每个 `catalog.json` 必须包含：

- `id`：稳定 lower snake case ID；
- `version`：语义版本；
- `name` 和 `description`；
- `blueprintSchemaVersions`；
- `runtimeVersions`；
- `provides`：提供的能力 ID；
- `requires`：依赖的能力 ID；
- `allowedDependencies`：允许组合的包 ID；
- `migrationsVersion`；
- `entrypoints`：运行时、UI、种子和测试入口；
- `uiSlots`：使用的固定扩展槽。

目录加载时执行结构和语义校验。包 ID、版本、入口文件或能力声明缺失时，组合器不得继续。

## 5. 领域包接口

### 5.1 蓝图片段

蓝图片段使用现有蓝图字段，但允许声明以下组合元数据：

- `owns`：本包拥有的实体、模块、流程和角色；
- `extends`：目标扩展点及补充字段、关系、权限或仪表盘；
- `requiresEntities`：必须由其他包提供的实体；
- `requiresCapabilities`：必须满足的能力；
- `mergeRules`：唯一允许的显式合并规则；
- `unsupportedWhen`：已知不可组合条件。

片段不允许声明 SQL、脚本、动态表达式或任意 React 代码。

### 5.2 运行时插件

运行时插件导出固定描述符：

```text
id
version
blueprintSchemaVersions
runtimeVersions
validateConfig(config)
registerMigrations(registry)
registerServices(registry)
registerIpc(registry)
registerUiExtensions(registry)
registerAcceptanceScenarios(registry)
```

所有注册表由底座提供，只暴露受限方法。插件不能访问或替换底座内部的会话、权限、审计、迁移和备份实现。

### 5.3 领域事务

领域事务服务接收：

- 当前 actor；
- 已打开的底座事务；
- 已验证的输入 DTO；
- 蓝图中本包的只读配置；
- 受限的实体仓储和审计接口。

服务不得自行创建数据库连接、绕过权限、写入任意表、读取渲染层状态或访问网络。

## 6. 组合器

### 6.1 输入和输出

输入：

- 已选择的领域包 ID 及锁定版本；
- 软件主题和项目级字段覆盖；
- 启用的角色与可选能力；
- 用户确认的未覆盖需求。

输出：

- 完整业务蓝图；
- 插件锁文件；
- 合并报告；
- 组合测试清单；
- 仍未覆盖的需求。

### 6.2 依赖解析

组合器按能力 ID 和允许依赖解析包图：

1. 加载并验证所有选中包目录；
2. 解析 `requires` 到唯一提供者；
3. 验证依赖在 `allowedDependencies` 中；
4. 检测缺失、多提供者歧义和循环依赖；
5. 生成稳定拓扑顺序；
6. 按顺序合并蓝图片段；
7. 生成精确版本锁文件。

依赖图必须无环。相同输入必须产生字节稳定的蓝图和锁文件。

### 6.3 命名和所有权

- 所有实体、模块、流程、角色、能力和扩展点使用稳定 ID；
- 中文名称仅用于展示，不能参与匹配；
- 每个对象只有一个所有者；
- 非所有者只能通过目标包公开的扩展点补充内容；
- 包不能修改另一个包的私有字段、状态或迁移。

### 6.4 冲突处理

以下情况直接失败：

- 重复拥有同一 ID；
- 扩展不存在的目标或未公开扩展点；
- 同一字段出现不同类型、必填、唯一或删除策略；
- 同一权限键含义冲突；
- 流程状态或转换被静默覆盖；
- 菜单 route 冲突；
- UI 槽位要求互斥；
- 演示数据唯一键冲突。

显式合并规则只允许追加、受约束覆盖展示属性、扩展枚举选项和向公开流程扩展点增加转换。任何规则都必须记录来源包和最终结果。

## 7. UI 扩展边界

插件只能注册到以下固定槽位：

- `entity.detail.tabs`：详情页标签；
- `entity.detail.actions`：详情操作区；
- `dashboard.sections`：仪表盘业务区；
- `form.field.renderers`：经注册的特殊字段渲染器；
- `report.sections`：报表内容区。

插件不得替换：

- 登录与会话页面；
- 主导航和顶栏；
- 权限拒绝、错误和维护页面；
- 通用列表、分页和危险操作确认；
- 备份恢复安全流程。

UI 扩展必须通过显式 ID 注册，使用底座 DTO 和业务 API，不直接调用 IPC 或数据库。

## 8. 六类领域包

### 8.1 台账与资产 `asset_registry`

核心实体：资产分类、资产、责任关系、资产状态事件。

主要规则：

- 资产编码唯一；
- 状态变更追加事件；
- 存在未完成关联业务时禁止停用；
- 存在历史记录时禁止硬删除；
- 责任人和分类引用必须有效。

主要扩展点：允许巡检、工单和项目包为资产增加受控关系及详情标签。

### 8.2 工单与服务 `work_order_service`

核心实体：服务目录、工单、工单事件、SLA 配置。

状态：待分派、待受理、处理中、待复核、已关闭。

主要规则：

- 无处理记录不能提交解决；
- 处理人与复核人权限分离；
- 已关闭工单不可普通编辑；
- SLA 按创建及复核关闭时间计算；
- 每次流转写入事件和审计。

公开扩展点：告警转单、巡检异常转单、库存领用关联和项目任务关联。

### 8.3 巡检与整改 `inspection_rectification`

核心实体：巡检计划、巡检任务、检查项、巡检明细、异常整改关系。

状态：计划中、执行中、待复核、已归档。

主要规则：

- 检查项不能为空且同任务不得重名；
- 所有检查项完成后才能提交；
- 异常项必须关联整改工单；
- 整改工单未关闭不能归档；
- 归档后明细不可修改。

依赖：可独立记录异常；启用闭环整改时需要 `work_order_service` 提供工单能力。

### 8.4 库存与批次 `inventory_batch`

核心实体：物料、仓库、批次、库存余额、库存流水、领用单和退库单。

主要规则：

- 余额变化和流水同事务保存；
- 不允许负库存；
- 按批次追踪生产、到期和入库日期；
- 退库不能超过原领用未退数量；
- 效期预警来自真实批次日期；
- 已发生流水的批次不可硬删除。

公开扩展点：申请审批后领用、项目任务领料和资产备件关联。

### 8.5 项目与任务 `project_task`

核心实体：项目、里程碑、任务、风险、交付物和任务事件。

主要规则：

- 任务状态变化更新项目进度汇总；
- 项目进度来自实际任务权重，不允许任意填写；
- 里程碑完成前校验必需任务和交付物；
- 未关闭高风险项阻止项目关闭；
- 历史任务和交付版本保留。

公开扩展点：工单关联任务、库存领料、交付物归档和项目申请审批。

### 8.6 申请与归档 `application_archive`

核心实体：申请单、审批节点、审批记录、文件版本、证照和到期提醒。

主要规则：

- 审批记录只追加；
- 当前审批人由节点和角色决定；
- 驳回与撤回遵守明确状态规则；
- 归档后正文不可直接修改；
- 新版本保留旧文件元数据；
- 到期提醒基于真实日期，不宣称外部通知已送达。

公开扩展点：库存领用审批、项目立项/交付审批和领域文档归档。

## 9. 常用组合

### 9.1 台账 + 工单

工单引用资产；资产详情显示工单；有未关闭工单时禁止停用资产。

### 9.2 台账 + 巡检

巡检计划选择资产；资产详情显示巡检历史；异常状态纳入资产活动情况。

### 9.3 巡检 + 工单

异常项在同一事务中创建整改工单及关联；工单关闭后才允许巡检归档。

### 9.4 库存 + 申请

批准领用申请后执行扣减事务；拒绝、撤回或审批失败不改变库存。

### 9.5 项目 + 任务

任务与里程碑直接组成项目进度；风险和交付物参与关闭条件。

### 9.6 项目 + 归档

项目交付物在审核后形成不可变归档版本，并保留项目关系。

### 9.7 申请 + 归档

已完成审批的申请及附件形成归档版本；审批记录保持追加式。

### 9.8 台账 + 工单 + 巡检

作为参考规模验收组合，覆盖资产、服务、工单、巡检、异常整改、角色权限、仪表盘和审计。

## 10. 版本和锁文件

组合结果生成 `domain-lock.json`，记录：

- 包 ID 和精确版本；
- 包内容摘要；
- 蓝图片段摘要；
- 兼容的蓝图和底座版本；
- 迁移版本；
- 依赖解析顺序；
- UI 扩展入口摘要。

运行时不使用版本范围解析。升级必须由生成器重新解析、执行迁移并运行受影响的单包及组合测试。

## 11. 错误模型

组合器使用稳定错误码：

- `PACK_CATALOG_INVALID`；
- `PACK_NOT_FOUND`；
- `PACK_VERSION_INCOMPATIBLE`；
- `CAPABILITY_MISSING`；
- `CAPABILITY_AMBIGUOUS`；
- `DEPENDENCY_NOT_ALLOWED`；
- `DEPENDENCY_CYCLE`；
- `OWNERSHIP_CONFLICT`；
- `EXTENSION_POINT_UNKNOWN`；
- `MERGE_CONFLICT`；
- `UI_SLOT_CONFLICT`；
- `SEED_CONFLICT`；
- `COMPOSED_BLUEPRINT_INVALID`。

错误包含领域包、JSON Pointer 路径和可读说明，不包含源码堆栈、SQL、文件系统敏感路径或用户输入全文。

运行时领域事务失败时：

- 当前 SQLite 事务整体回滚；
- 记录脱敏失败审计；
- 返回领域稳定错误码；
- 不保留部分余额、部分状态或孤立关联。

## 12. 测试策略

### 12.1 目录和组合器单元测试

覆盖目录结构、版本兼容、能力解析、循环依赖、拓扑稳定性、所有权、扩展点、冲突及锁文件确定性。

### 12.2 单包集成测试

每个包至少覆盖：

- 建库和迁移；
- 正常业务流程；
- 权限拒绝；
- 非法状态；
- 唯一、引用和版本冲突；
- 核心事务回滚；
- 审计与历史不可篡改；
- 确定性演示数据。

### 12.3 组合测试

首版强制矩阵：

| 组合 | 核心断言 |
|---|---|
| 台账 + 工单 | 资产停用限制和工单关联 |
| 台账 + 巡检 | 资产计划、执行和历史 |
| 巡检 + 工单 | 异常转单及关闭后归档 |
| 库存 + 申请 | 批准扣减、拒绝不扣减 |
| 项目 + 任务 | 里程碑、进度和风险汇总 |
| 项目 + 归档 | 交付物版本和归档保留 |
| 申请 + 归档 | 审批记录及归档不可修改 |
| 台账 + 工单 + 巡检 | 参考规模端到端验收 |

### 12.4 参考规模验收

“台账 + 工单 + 巡检”组合至少包含：

- 8 个实际可用功能模块；
- 8 张以上业务及系统表；
- 调度、处理、复核和管理员角色；
- 工单和巡检两条完整流程；
- 异常转工单跨实体事务；
- 1000 条级别确定性主业务演示数据；
- 真实仪表盘统计；
- Electron E2E、重启持久化和安装包验证。

## 13. 实施分解

该子项目拆为八个可独立验收的实施单元：

1. 领域包协议、目录加载器和组合器；
2. 台账与资产包；
3. 工单与服务包；
4. 巡检与整改包及前三包参考组合；
5. 库存与批次包；
6. 项目与任务包；
7. 申请与归档包；
8. 双包矩阵、参考规模 E2E 和版本锁定验收。

前三包完成后可以验证企业运维核心闭环，但首版发布仍必须完成全部八项。

## 14. 验收标准

本子项目完成必须满足：

1. 六个领域包均有有效目录、蓝图片段、运行时插件、种子和测试；
2. 相同输入产生字节稳定蓝图和锁文件；
3. 缺失、循环、冲突和不兼容组合在构建阶段失败；
4. 八组强制组合矩阵全部通过；
5. 核心事务失败不会留下部分业务数据；
6. UI 扩展只能进入固定槽位；
7. 参考规模组合达到模块、数据、角色和流程要求；
8. 现有蓝图校验器、桌面底座及旧生成器回归套件继续通过；
9. 本阶段不改变“开始生成.bat”的现有行为；
10. 未覆盖专业要求在组合报告中明确披露。
