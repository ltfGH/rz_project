# 领域组合矩阵与参考应用验收设计

## 1. 目标

完成领域原型子项目的最后一个实施单元：把已经交付的六个核心领域包通过正式生产桥接包组合起来，并以“资产台账 + 工单服务 + 巡检整改”真实 Electron 应用完成参考规模端到端验收。

本阶段必须同时证明：

- 跨领域规则由明确的领域模块和 SQLite 事务实现，而不是通用 CRUD 或仅供测试使用的胶水代码；
- 领域包能够被桌面运行时真实发现、校验、激活并暴露给渲染进程；
- 组合项目可以稳定生成约 1000 条确定性业务数据并完成真实业务闭环；
- 应用重启、重复生成和 Windows 安装包交付均可验证；
- 生成结果记录精确版本，后续升级不会静默改变既有业务规则。

## 2. 范围与非目标

本阶段负责：

- 新增五个正式生产桥接包；
- 将现有 `domain_document_bridge` 纳入统一生产桥接目录和验收；
- 把类型化领域命令总线提升为共享运行时能力；
- 建立生产插件目录、插件宿主和插件贡献激活流程；
- 完成八组强制组合矩阵；
- 建立独立的参考应用配置、确定性种子、Electron E2E 和安装包验收；
- 生成交付级版本锁文件和升级边界。

本阶段不负责：

- 面向最终用户的拖拽式低代码编辑器；
- 任意包之间自动推导业务关系；
- 通用脚本、动态 SQL 或任意 React 代码执行；
- 在线服务、消息队列、云数据库或外部通知；
- 将参考应用固化为所有项目必须使用的模板；
- 对已经验收的核心领域状态机做无关重构。

## 3. 总体架构

系统在现有蓝图、桌面底座和领域包之上增加三层：

1. **生产桥接层**：拥有跨包关系、跨包规则和必要 UI 扩展。
2. **生产插件宿主层**：发现、校验、排序并激活核心包和桥接包贡献。
3. **参考应用验收层**：使用正式装配路径生成、运行、重启并打包一个真实应用。

```text
project blueprint + domain-lock.json + project.lock.json
                         |
                         v
              production plugin catalog
                         |
                         v
                 desktop plugin host
          +--------------+--------------+
          |              |              |
     core packs      bridge packs   shared runtime
          |              |          command bus
          +--------------+--------------+
                         |
                         v
           generic desktop runtime + SQLite
                         |
                         v
        reference application / generated project
```

核心包继续拥有各自实体和状态机。桥接包只能使用双方公开扩展点，不得修改核心包私有表、直接覆写状态或复制核心状态机。

## 4. 生产桥接包

### 4.1 统一约束

五个新桥接包与现有 `domain_document_bridge` 使用和核心包相同的生产描述符、目录校验、版本校验、迁移注册、服务注册、IPC 注册、UI 扩展和验收场景接口。

桥接包可以拥有：

- 为跨包关系所需的关联实体；
- 目标核心包公开允许的补充字段和关系；
- 只调用公开领域服务的处理器；
- 固定槽位中的详情标签、操作入口和仪表盘区块；
- 自己的角色，但只有在现有角色无法表达最小权限时才能新增。

桥接包不得：

- 直接更新另一包拥有的状态字段；
- 绕过领域服务执行原始 SQL；
- 获取任意数据库连接或文件系统句柄；
- 在渲染进程中拼装跨包事务；
- 复制另一包的审批、库存、工单或归档规则。

### 4.2 `asset_work_order_bridge`

职责：

- 为工单补充可选资产引用和稳定创建来源；
- 在资产详情页提供关联工单标签和从资产创建工单入口；
- 向资产停用扩展点注册阻断器：存在未关闭关联工单时禁止停用；
- 在工单创建和关系写入之间保持同一事务。

已关闭工单保留历史关系，但不再阻止资产停用。桥接包不改变工单自身的分派、处理、复核和关闭状态机。

### 4.3 `asset_inspection_bridge`

职责：

- 为巡检计划和任务补充资产引用；
- 在资产详情页提供计划、执行记录、异常和归档历史；
- 向资产停用扩展点注册阻断器：存在未归档巡检任务时禁止停用；
- 校验被引用资产存在且处于允许安排巡检的状态。

已归档任务保留完整历史。桥接包不替代巡检包的检查项、提交、复核和归档规则。

### 4.4 `inspection_work_order_bridge`

职责：

- 拥有巡检异常与整改工单之间的稳定关联；
- 注册异常处理器，在同一事务中创建工单并写入关联；
- 使用幂等键保证同一异常不会重复创建整改工单；
- 向巡检归档扩展点注册阻断器：关联工单未关闭时禁止归档；
- 在巡检和工单详情页分别展示对端关系。

创建工单、关系、工单事件和审计任一步失败时全部回滚。工单关闭只解除归档阻断，不直接替巡检包执行归档。

### 4.5 `inventory_application_bridge`

职责：

- 为领用申请补充批次、数量和用途关系；
- 在最终审批完成处理器中调用库存出库命令；
- 以受限的桥接系统身份执行库存领域命令，保留原申请人、审批人和触发申请信息；
- 使用申请编号和审批轮次组成幂等键，防止重复扣减；
- 提供申请详情中的库存批次、扣减流水和失败原因摘要。

只有最终审批成功才允许扣减库存。驳回、撤回、中间节点批准和任何事务失败均不得改变库存。审批状态、审批记录、库存余额、库存流水和审计必须处于同一事务边界。

### 4.6 `project_archive_bridge`

职责：

- 拥有 `project_delivery_archive` 关联实体；
- 由归档管理员将项目交付物版本关联到 `ready` 文件版本；
- 保留项目、交付物版本、文件版本和归档时间的不可变关系；
- 向项目关闭扩展点注册阻断器：必需交付物没有有效归档关系时禁止关闭；
- 在项目和归档详情页展示双向关系。

桥接包不修改已经完成的交付物版本，也不把文件元数据复制为新的归档实现。

### 4.7 `domain_document_bridge`

现有桥接包继续负责领域对象与托管文档版本的不可变关联。本阶段只将其注册到统一生产目录，并纳入版本锁定、组合验证和回归测试，不扩大其业务范围。

## 5. 共享领域命令总线

现有申请归档包中的类型化命令总线提升到领域包共享运行时模块。迁移后申请归档包保持原有公开行为，其他桥接包复用同一实现。

命令注册项包含：

- 稳定命令 ID；
- 输入验证器和最大负载限制；
- 允许调用的来源包与角色；
- 在当前事务中执行的处理器；
- 稳定成功 DTO 和领域错误码。

总线必须：

- 只接受 JSON 数据，不接受函数、原型对象或任意类实例；
- 拒绝未注册命令、未知字段、危险对象键和越界负载；
- 使用当前请求已经打开的 SQLite 事务，不自行创建旁路连接；
- 在提交前完成领域写入和成功审计；
- 对重试命令校验幂等键并返回既有结果；
- 对 UI 返回脱敏错误，不暴露 SQL、堆栈或本机路径。

失败审计不能破坏业务原子性。事务内的成功审计随业务一起提交或回滚；可选的事务外失败诊断只能记录脱敏的命令 ID、错误码和关联 ID，不能伪装为已提交的业务审计。

## 6. 生产插件目录与桌面宿主

### 6.1 插件目录

新增生产插件目录，显式收录六个核心包、五个新桥接包和现有 `domain_document_bridge`。目录项记录插件 ID、精确版本、能力、依赖、入口和内容摘要。

桌面主进程不再使用空的 `PluginRegistry`。启动顺序为：

1. 读取并验证项目蓝图和锁文件；
2. 从生产目录解析蓝图声明的插件；
3. 校验依赖、版本、摘要和拓扑顺序；
4. 注册迁移并完成数据库升级；
5. 激活服务、命令、阻断器、完成处理器、UI 和验收贡献；
6. 注册通用及插件 IPC；
7. 创建窗口。

任一插件缺失、摘要不符、依赖不兼容或贡献冲突时启动失败关闭，不允许降级为只有通用 CRUD 的残缺应用。

### 6.2 插件宿主

宿主提供受限注册表：

- `migrationRegistry`；
- `serviceRegistry`；
- `domainCommandRegistry`；
- `lifecycleBlockerRegistry`；
- `completionHandlerRegistry`；
- `ipcContributionRegistry`；
- `uiExtensionRegistry`；
- `acceptanceScenarioRegistry`。

注册完成后冻结注册表。插件运行期间只能通过注入接口调用服务，不能取得宿主内部对象。贡献 ID 重复、目标扩展点不存在或依赖未激活时直接失败。

### 6.3 IPC 与 UI

插件 IPC 由宿主统一分发，并沿用桌面底座的会话、权限、输入验证、错误映射和审计流程。渲染进程只能调用暴露在预加载层中的白名单命令。

UI 扩展继续限定在公开槽位。参考应用至少呈现以下 12 个可用模块或业务视图：仪表盘、资产分类、资产台账、巡检计划、巡检任务、巡检记录与异常、工单调度、工单处理、工单复核、用户与角色、审计日志、备份恢复。每项都必须有真实数据、权限和可执行操作，不通过空白占位页面计数。

## 7. 参考应用

### 7.1 定位与装配

参考应用是生成器的正式验收样本，不是固定模板。它必须使用和普通生成项目相同的组合器、锁文件、插件目录、桌面运行时和打包链路。

选择：

- 核心包：`asset_registry`、`work_order_service`、`inspection_rectification`；
- 桥接包：`asset_work_order_bridge`、`asset_inspection_bridge`、`inspection_work_order_bridge`；
- 桌面底座：认证、权限、审计、仪表盘、备份恢复和 SQLite 持久化。

资源复制和构建脚本接受显式项目配置路径。现有运行时测试夹具继续独立存在，参考应用资源不能覆盖通用夹具。

### 7.2 角色与账号

参考应用至少提供：

- 调度员：创建巡检计划、创建并分派工单；
- 处理人：执行巡检、记录异常、受理和处理工单；
- 复核人：复核工单和巡检结果；
- 管理员：管理基础数据、查看审计、执行备份恢复和诊断。

验收账号只使用确定性测试凭据，并在交付说明中明确标记为演示账号。生产首次启动仍遵循现有密码初始化和修改规则。

### 7.3 确定性数据

统一种子生成器接受固定无符号 32 位种子、记录规模和基准时间。相同输入必须产生字节稳定的业务数据和相同统计摘要。

默认种子精确生成 1000 条计数范围内的业务记录，包括资产、分类、责任关系、巡检计划、巡检任务、检查项、巡检明细、异常关系、工单和工单事件。种子报告按表列出数量并断言合计为 1000。审计、系统账号、权限和迁移元数据不计入该数量，但仍须生成满足验收流程所需的数据。

数据必须满足：

- 外键、唯一约束和时间先后关系有效；
- 各主要状态都有代表性记录；
- 异常、超时、待复核和已关闭记录能够驱动真实仪表盘；
- 不包含真实企业、个人、设备编号或敏感凭据；
- 批量插入失败时整批回滚，不能留下半套演示数据。

### 7.4 核心验收流程

Electron E2E 必须通过 UI 和白名单 IPC 完成：

1. 调度员登录并创建资产关联的巡检计划；
2. 处理人执行巡检并提交一个异常结果；
3. 异常处理在同一事务中创建整改工单和关联；
4. 验证重复提交不会创建第二张工单；
5. 验证工单未关闭时巡检不能归档；
6. 验证未归档巡检或未关闭工单存在时资产不能停用；
7. 处理人填写处理记录并提交解决；
8. 复核人关闭工单并复核、归档巡检；
9. 管理员停用资产并核对审计和仪表盘；
10. 关闭并重新启动 Electron，确认 SQLite 数据、关系和状态全部保留。

E2E 同时覆盖越权、非法状态和事务注入失败。失败后必须确认工单、关系、业务事件和审计没有部分残留。

## 8. 强制组合矩阵

八组矩阵均须有正向流程、权限拒绝、非法状态、事务回滚和精确蓝图断言；不适用的失败类型必须在测试中明确说明。

| 组合 | 实现归属 | 核心断言 |
|---|---|---|
| 资产 + 工单 | `asset_work_order_bridge` | 资产关联、详情历史、未关闭工单阻止停用 |
| 资产 + 巡检 | `asset_inspection_bridge` | 资产计划、执行历史、未归档巡检阻止停用 |
| 巡检 + 工单 | `inspection_work_order_bridge` | 异常原子转单、关闭工单后才可归档 |
| 库存 + 申请 | `inventory_application_bridge` | 最终批准扣减，拒绝、撤回和失败不扣减 |
| 项目 + 任务 | `project_task` 核心包 | 里程碑、加权进度、高风险关闭阻断 |
| 项目 + 归档 | `project_archive_bridge` | 交付版本不可变关联、缺少归档阻止关闭 |
| 申请 + 归档 | `application_archive` 核心包 | 审批记录只追加、归档正文和版本不可变 |
| 资产 + 工单 + 巡检 | 参考应用 | 角色、双流程、异常转单、持久化和打包 |

组合测试使用正式生产描述符和插件宿主，不能手工调用内部类来绕过真实装配路径。

## 9. 事务、幂等与恢复

所有跨包写操作由桌面宿主打开一个 SQLite 事务，并把受限事务上下文传入领域命令总线。任何领域校验、条件更新、关联写入、事件或审计失败时整体回滚。

幂等键至少覆盖：

- 巡检异常转工单：异常稳定编号；
- 申请批准扣库存：申请编号 + 审批轮次；
- 项目交付归档：项目编号 + 交付物版本 + 文件版本。

相同幂等键和相同载荷返回既有结果；相同键但不同载荷返回稳定冲突错误。SQLite 唯一约束是最终防线，不能只依赖进程内缓存。

异常退出依赖 SQLite 原子事务恢复，不增加消息队列或复杂补偿任务。可恢复的文件操作继续遵守申请归档包既有 staged/ready/failed 协议。

## 10. 版本锁定与升级

保留现有 `domain-lock.json`，用于记录领域包解析结果、内容摘要、拓扑顺序、迁移版本和 UI 入口摘要。

新增交付级 `project.lock.json`，记录：

- 生成器版本和蓝图规范版本；
- `domain-lock.json` 的 SHA-256；
- 核心包与桥接包精确版本；
- 数据库结构版本；
- 桌面运行时、Electron、Node.js 和 SQLite 版本；
- 项目配置规范化摘要；
- 构建目标和锁文件格式版本。

锁文件使用稳定键顺序和规范化 JSON。相同输入重复生成时，两份锁文件和生成结果必须稳定。运行时只接受精确版本，不解析版本范围。

升级必须显式执行：重新解析依赖、生成锁文件差异、运行迁移、执行受影响单包和组合测试，并输出升级报告。未声明迁移路径、摘要不匹配或测试失败时拒绝升级；不得静默替换领域规则。

## 11. 构建与安装包验收

参考应用沿用现有 Electron Builder 和 Windows NSIS 链路。验收分为：

1. 构建生产资源和 Electron 主进程、预加载层、渲染层；
2. 对未打包目录执行启动和核心流程冒烟；
3. 构建 Windows 安装包；
4. 在隔离的临时安装目录执行静默安装或等价可重复安装；
5. 启动安装后的应用并确认主窗口、数据库初始化和插件清单；
6. 退出后验证没有把临时数据库、日志、凭据或安装产物加入仓库。

CI 不具备 Windows 安装能力时可以跳过安装步骤，但本地发布验收不得跳过，并需保存机器可读报告。安装包验收失败不能标记第一版完成。

## 12. 测试策略

### 12.1 单元测试

覆盖桥接配置、描述符、依赖、输入验证、错误码、幂等键、阻断器、命令白名单、锁文件规范化和确定性种子。

### 12.2 SQLite 集成测试

每个桥接包使用真实 SQLite 数据库验证正常事务、权限拒绝、状态阻断、并发版本冲突、唯一约束、回滚、重试和审计。

### 12.3 组合与回归测试

八组矩阵从正式目录装配完整蓝图，验证所有权、扩展点、迁移顺序、UI 槽位、权限合并和锁文件。六个核心包、蓝图验证器、桌面运行时及旧生成器回归必须继续通过。

### 12.4 Electron E2E
